Once a TLS Session is established between the two TLS end points, the execution of role-based 318 
client AuthZ is a two-step process.  319 
 320 
During the first step, the mbaps server obtains the x.509v3 client domain certificate. This step 321 
occurs when the mbaps server receives message 8 as shown in Figure 6 TLS Full Handshake 322 
Protocol. The role is extracted from the x.509v3 certificate and cached. If a session is resumed, 323 
this role must be associated with the resumed session. 324 
 325 
The role extension is an ASN1 encoded UTF8 string. 326 
 327 
 328 
Figure 9 Example Role Extension 329 
In the example Role extension, shown in Figure 9 Example Role Extension, the Role value 330 
is ’Operator’. 331 
 332 
The second step of the mbaps role-based client AuthZ capability involves using the extracted 333 
client Role and the Modbus request. Both fields are input to the mbaps AuthZ Algorithm. The 334 
AuthZ Algorithm determines whether the client is AUTHORIZED or NOT_AUTHORIZED to 335 
perform the indicated function on the indicated resource that was specified in the Modbus 336 
Function Code received by the mbaps server using the provisioned Roles-to-Rights Rules 337 
Database. If the request is NOT_AUTHORIZED, Modbus exception code 01 – Illegal function 338 
code will be returned. If the request is AUTHORIZED, it will be processed as normal by the mbap 339 
server.  340 
 341 
The Authorization Function and Roles-to-Rights Rules Database may exist on the server device 342 
or may be remote requiring a separate protocol to determine the authorization status of the 343 
request. This is outside the scope of this document. 344
