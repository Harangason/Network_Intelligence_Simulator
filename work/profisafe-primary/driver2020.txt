In a first step the PSD uses the transfer functions to send the synchronization data to the

i.e. within a device-specific synchronization timeout. Different data for flow control or a CRC 
value send the PSD to the PSD_HARD_FAIL state.

2.2.1 Description of the states 
PSD_OPERATION 
After successful initialization, the F-slave starts its operation, which is shown above as 
PSD_OPERATION. This includes the following states relevant for the PROFIsafe 
communication. 
PSD_INIT 
The PSD state is entered when the psd_InitInstance(…) function has been executed for a 
communication instance without errors. The PSD instance is initialized correctly in this state, 
but it was not configured or called the psd_FParBuild(...) function with invalid F-parameters. 
PSD_PARAM 
The psd_FParBuild(...) function was called with invalid F-parameters. 
The configuration of the user data lengths must be made in this state with the PSD function 
psd_Config(…). 
 A PSD instance is ready for cyclic data exchange when: 
• Valid F-parameters exist and 
• A valid configuration of the user data lengths exists. 
PSD_DATAEX 
The cyclic data exchange with the F-host has been started. The psd_Run(…) function was 
called for the communication instance. The cyclic processing of input/output frames begins 
as soon as the toggle bit changes from 0 to 1 in the control byte of the output frame. New F-
parameters or a reconfiguration of user data lengths are rejected in this PSD state.  
PSD_HARD_FAIL 
The PSD instance has established an inconsistency, probably due to a hardware fault. At a 
transition to the PSD state PSD_HARD_FAIL the PSD sets the interface variable "psd_SafetyVar" 
to the value "P_SAFETY_CONST_FALSE". The PSD instance calls the hard_err( …) function of 
the F-application. With the hard_err(…) function, the F-application sets the safe state (for 
example, the specific safety values in the output process data and the input frame section) 
for all communication instances.

2.2.2 Description of the state transitions 
START → PSD_INIT 
After PowerOn, the F-application initializes the respective communication instance by calling 
psd_InitInstance(…). Once it runs error-free, the communication instance is in the PSD_INIT 
state. 
F-CYCLE → PSD_HARD_FAIL 
Any inconsistency or any hardware fault detected by the PSD, always results in the 
PSD_HARD_FAIL state for all PSD instances. 
PSD_INIT → PSD_PARAM 
The stack signals the receipt of F-parameters to the F-application. The F-application then 
configures the communication instance by calling the psd_FParBuild(…) function. The 
PSD_PARAM state is reached when valid F-parameters exist. 
PSD_PARAM → PSD_INIT 
The stack signals the receipt of F-parameters to the F-application. The F-application then 
reconfigures the communication instance by calling the psd_FParBuild(…) function. The 
psd_FParBuild(…) function has detected an invalid F-parameter. 
PSD_PARAM → PSD_PARAM 
After receipt of new F-parameters from the stack, the F-application reconfigures the 
communication instance. The PSD_PARAM state remains as long as valid F -parameters are 
present. (See section F-input or F-output user data area (Page 77)) 
PSD_PARAM → PSD_PARAM 
The lengths for the input and output user data must be set with the psd_Config(...) function 
for each communication instance. The maximum permissible lengths are set for each 
instance in p_c_config.h. The optional values passed by the F-application must be less than or 
equal to the values of p_c_config.h. 
PSD_PARAM → PSD_DATAEX 
The stack signaled to the F-application the transition to cyclic data exchange for a particular 
communication instance with [RUN]. The F-application then calls the psd_Run(…) function. 
PSD_DATAEX → PSD_PARAM 
The stack signaled to the F-application the exit from cyclic data exchange for a particular 
communication instance with [STOP]. The F-application then calls the psd_Stop(…) function.

4.1 PSD interface functions 
The PSD can be used in different system environments. This is achieved with the following 
features: 
• You can adapt a specific F-application or stack interface by programming the interface 
functions from p_c_fapplication.h or p_c_si.h.

• The PSD detects the byte order "big endian" or "little endian" of hardware it uses. The PSD 
is not tested for 2-channel F-slaves, in which the two channels are operated with a 
different byte order. This must be taken into consideration for the synchronization of the 
F-application. 
• With the memory attributes for the memory segment control that be set in p_c_config.h, 
the storage location of data and code can be configured to match the tool chain.  
• Additional settings for hardware architecture or memory model can be made with the 
generation parameters in p_c_config.h.

4.1.3 psd_Config(...) 
Configuration of the I/O data lengths for input and output user data for a PSD instance.  
The I/O data lengths for the input and output user data can be configured as static or dynamic 
according to the setting in psd_InitInstance(...). 
Variant "static" 
The psd_Config(...) function uses the lengths defined in p_c_config.h 
(OUTDATA_MAX_LEN_INST_xx / INDATA_MAX_LEN_INST_yy). It is not possible to reconfigure 
to a smaller length. 
Variant "dynamic": 
The psd_Config(...) function uses the lengths from p_c_config.h as maximum values. 
Reconfiguring to smaller lengths is possible in PSD_PARAM state.  
When the I/O data lengths are configured, the lengths are read out via the 
psd_GetConfigPtr(...) function. 
When a data length exceeds the maximum value set in p_c_config.h, the PSD goes to the 
instance-global PSD_HARD_FAIL state. 
The psd_Config(...) function must be called in the PSD_PARAM PSD state. Successful 
implementation is a prerequisite for the transition to the PSD_DATAEX state, even if the 
"static" variant was set. psd_FParBuild(...) must have been executed successfully prior to the 
call. 
Configuration of the I/O data lengths is rejected in the PSD_DATAEX and PSD_INIT states with 
FPAR_CONFIG_NOT_POSSIBLE.

system architecture used and lies in the responsibility of the F-slave development.
