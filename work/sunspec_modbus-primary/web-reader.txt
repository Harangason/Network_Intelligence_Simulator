L88@P5: 1 Introduction
L89@P5: Modbus, defined by Modbus.org, was designed for use in isolated, "air-gapped" industrial
L90@P5: networks where physical access was the primary security measure. In modern DER and
L91@P5: industrial internet of things (IIoT) environments, it is necessary to provide additional security
L92@P5: features in the communication protocol. For this reason, the SunSpec Alliance initiated an
L93@P5: effort to establish a secure implementation of Modbus based on contemporary security
L94@P5: practices. Secure SunSpec Modbus provides a standardized set of requirements for
L95@P5: implementing a secure implementation of Secure SunSpec Modbus TCP, particularly for grid
L96@P5: control applications such as those described in the IEEE 1547-2018 standard. The Secure
L97@P5: SunSpec Modbus TCP implementation incorporates mutual TLS with an X.509 extension to
L98@P5: provide confidentiality, integrity, authentication, and authorization based on the MODBUS/TCP
L99@P5: Security Protocol Specification.
L100@P5: 1.1 Security Principles
L101@P5: Secure SunSpec Modbus TCP provides the following security features:
L102@P5: • Confidentiality: TLS encrypts all data transmitted between the client and server,
L103@P5: preventing eavesdropping and data exposure.
L104@P5: • Authentication: TLS uses digital certificates (Public Key Infrastructure) to provide
L105@P5: mutual authentication, ensuring that both the client and the server are who they claim to
L106@P5: be.
L107@P5: • Integrity: TLS provides data integrity checks to ensure that the message has not been
L108@P5: altered during transmission.
L109@P5: • Anti-Replay Protection: TLS is designed to prevent replay attacks by using sessionspecific keys and sequences.
L110@P5: • Authorization: The protocol can also use information embedded in the certificates (such
L111@P5: as user and device roles) to implement role-based access control (RBAC), allowing for
L112@P5: more granular authorization in DER grid control environments.
L113@P5: 1.2 Document Organization
L114@P5: Chapter 2 includes the normative references that provide links to the specifications mentioned in this
L115@P5: document.
L116@P5: Chapter 3 covers the Secure SunSpec Modbus TCP Developments.
L117@P5: Chapter 4 discusses considerations for Secure SunSpec Modbus RTU.
L118@P5: Chapter 5 covers the Secure SunSpec Modbus TCP Requirements.

L167@P8: 3 Secure SunSpec Modbus TCP Development
L168@P8: The SunSpec Modbus workgroup gathered weekly for several months to select the
L169@P8: requirements for the Secure SunSpec Modbus Specification. During those conversations,
L170@P8: there were many difficult decisions regarding the security requirements and use cases of the
L171@P8: SunSpec specification. The following sections describe many of the critical decisions and why
L172@P8: the SunSpec implementation deviates from the modbus.org MODBUS/TCP Security
L173@P8: specification.
L174@P8: 3.1 Cipher Suites Selection
L175@P8: The MODBUS/TCP Security specification, last updated by Modbus.org in 2021, permits weak
L176@P8: cipher suites that use outdated encryption algorithms, short key lengths, vulnerable modes
L177@P8: (e.g., Cipher Block Chaining)
L178@P8: 1
L179@P8: , and absent Perfect Forward Secrecy (PFS). As a result, the
L180@P8: SunSpec working group modernized the cipher suite options while allowing for additional
L181@P8: ciphers to be added as standardized cryptography evolves. The group selected ciphers that
L182@P8: were widely available and lightweight for the embedded systems.
L183@P8: Devices must support the following TLSv1.2 cipher suites:
L184@P8: • TLS_ECDHE_ECDSA_WITH_AES_128_GCM_SHA256
L185@P8: • TLS_ECDHE_ECDSA_WITH_AES_128_CCM_8
L186@P8: and if the device supports TLSv1.3, they must provide the following cipher suites:
L187@P8: • TLS_AES_128_GCM_SHA256
L188@P8: • TLS_AES_128_CCM_SHA256
L189@P8: The list of required ciphers was kept to a minimum to improve interoperability. Further, IEEE
L190@P8: 2030.5—specified as a standard interface in the IEEE 1547 standard like SunSpec Modbus—
L191@P8: requires TLS_ECDHE_ECDSA_WITH_AES_128_CCM_8, so it was included because many
L192@P8: DER devices may already have software libraries and hardware components that support it.
L193@P8: 3.2 Authorization and Mandatory Roles
L194@P8: SunSpec adopted the MODBUS/TCP Security authorization approach to address the grid
L195@P8: operator use case—and took things further by mandating the X.509v3 certificate must include a
L196@P8: role. MODBUS/TCP Security states the role in the X.509v3 certificate MUST use
L197@P8: ASN.1:UTF8String encoding. There must only be one role defined per certificate and the entire
L198@P8: string is treated as a single role. SunSpec adopted this same approach and embedded the role
L199@P8: in the X.509v3 certificate with the Modbus.org Private Enterprise Number (PEN) OID
L200@P8: 1.3.6.1.4.1.50316.802.1.

L202@P8: required roles with these general permissions.

L735@P32: 6 Device Information Model Usage for Modbus
L736@P32: This section specifies Modbus Device Information Model instance encoding. An Information
L737@P32: Model instance includes the values associated with the defined content of a model.
L738@P32: 6.1 Device Modbus Map
L739@P32: Device Information Models are used to construct a device Modbus map. The Information
L740@P32: Models that represent the functionality implemented in the device are placed contiguously in the
L741@P32: Modbus address space at a defined location as specified in this section.
L742@P32: Figure 5: Device Modbus Map
L743@P32: All SunSpec Device Information Model maps MUST begin with the SunS identifier. The
L744@P32: identifier is followed sequentially by common, standard, and vendor Device Information Models,
L745@P32: as needed. An end model terminates the map. There is no requirement for any model ordering
L746@P32: other than the end model must be the last model in the sequence.
L747@P32: 6.1.1 Modbus Address Location
L748@P32: All Modbus device maps MUST be in the holding register address space.
L749@P32: The beginning of the device Modbus map MUST be located at one of three Modbus addresses
L750@P32: in the Modbus holding register address space: 0, 40000 (0x9C40) or 50000 (0xC350). These
L751@P32: Modbus addresses are the full 16-bit, 0-based addresses in the Modbus protocol messages.
L752@P32: The first two Modbus registers at the start address MUST have the following well-known
L753@P32: constant values as a marker: 0x5375, 0x6E53 (hexadecimal values of the ASCII string SunS).
L754@P32: 6.1.2 Information Models
L755@P32: The Device Information Models MUST be placed contiguously, beginning immediately after the
L756@P32: SunS marker registers. Each Information Model MUST have registers corresponding to all the
L757@P32: points in the Information Model, including those specified as optional or unimplemented. Points
L758@P32: in a model MUST be placed such that there are no additional Modbus registers between points
L759@P32: specified in the model definition. Points that are not supported or have no valid value MUST be
L760@P32: assigned the appropriate unimplemented value based on the point type. There MUST NOT be
L761@P32: additional Modbus registers between Information Models in the device Modbus map.
L762@P32: The length point (L) in an information model instance MUST be set to the remaining number of
L763@P32-33: Modbus registers in the model following the length point.SunSpec Device Information Model Specification 34 sunspec.org
L764@P33: A Modbus register map representing a Device Information Model MUST preserve the order of
L765@P33: points and groups defined within the model. Such Modbus register maps MUST have group
L766@P33: point elements placed before group elements, at lower register indices, and all instances of
L767@P33: repeated point or group elements MUST be consecutive.
L768@P33: 6.1.3 End Model
L769@P33: The last Information Model in the device Modbus map MUST be a two-register empty model
L770@P33: with a model ID of 0xFFFF and a model length of 0.
L771@P33: 6.2 Device Information Model Discovery
L772@P33: A discovery mechanism can be employed to determine the type and location of each of the
L773@P33: Information Models in the device map.
L774@P33: Device architects may choose to implement different collections of Information Models in
L775@P33: arbitrary order. In any implementation, after the Modbus address of a particular model is
L776@P33: determined, the Modbus location of the points in the model are then known based on the model
L777@P33: definition.
L778@P33: All Information Models start with an id register and a length register. This information is used to
L779@P33: step through or scan the Information Models even if the ID and contents of an Information Model
L780@P33: are not understood by the scanning application. This permits implementations to find and use
L781@P33: the Device Information Model(s) they understand and ignore those whose definitions are
L782@P33: unknown.
L783@P33: The following procedure is used for Information Model discovery:
L784@P33: 1. Read the contents of addresses 0, 40000, and 50000 until the well-known marker is
L785@P33: found.

L790@P33: register to determine the starting address of the subsequent Information Model.
